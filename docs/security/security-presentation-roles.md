# Распределение ролей для защиты Security / ЛЗ 7

## Абинсериков Нурасыл — риски, RAID, ПДн и итоговая координация

**Файлы:**

- `docs/security/raid.md`
- `docs/security/compliance-checklist.md`
- `docs/security/risk-assessment.md`

**Что рассказывает:**

Абинсериков Нурасыл представляет общую картину рисков проекта. В RAID-логе зафиксировано
20 рисков. Для каждого риска указаны вероятность, влияние в часах, EMV,
персональный владелец, стратегия реагирования, наблюдаемый триггер и дата
пересмотра.

EMV рассчитывается по формуле:

```text
EMV = вероятность × влияние
```

Суммарный риск-резерв проекта составляет **63,2 часа**. Отдельно выделен
управленческий резерв **16 часов** для неизвестных рисков. Эти резервы нельзя
смешивать: риск-резерв используется для известных рисков из RAID-лога, а
управленческий резерв расходуется только по отдельному решению спонсора.

В части ПДн проект обрабатывает email, имя пользователя, хэш пароля,
контактные данные заявки и технические данные для безопасности и диагностики.
Пароли не хранятся в открытом виде. Доступ к данным ограничивается ролями и
необходимостью выполнения рабочих операций.

До публичного запуска необходимо окончательно подтвердить основание обработки
данных, сроки хранения, порядок удаления, TLS и процедуру уведомления об
инцидентах. В текущем MVP ИИ-компонент отсутствует.

В конце Абинсериков Нурасыл подводит общий итог защиты и сообщает, какие security-задачи
остаются открытыми.

## Айдар Елнара — STRIDE, API, доступ, DoS и отказоустойчивость

**Файлы:**

- `docs/security/threat-model.md`
- `docs/security/threat-model.json`
- `docs/security/security-backlog.md`

**Что рассказывает:**

Айдар Елнара представляет архитектуру угроз. В модели показаны внешний пользователь,
браузер/Nginx, FastAPI API и PostgreSQL. Между компонентами отмечены границы
доверия и потоки данных.

Модель проверена по всем шести категориям STRIDE:

- **Spoofing** — подмена пользователя или администратора;
- **Tampering** — изменение цены, роли или количества мест;
- **Repudiation** — отрицание административного действия;
- **Information Disclosure** — раскрытие паролей или персональных данных;
- **Denial of Service** — перегрузка API или перебор авторизации;
- **Elevation of Privilege** — получение чужих прав.

Основные меры защиты API:

- JWT-аутентификация;
- проверка ролей на сервере;
- проверка владельца ресурса;
- Pydantic-валидация;
- серверный расчёт стоимости;
- транзакции PostgreSQL;
- блокировка выезда через `SELECT ... FOR UPDATE`;
- healthcheck и rate limit.

Отдельно Айдар Елнара рассказывает о мере **B-03**: ограничить auth/API, добавить
таймауты и ограничения reverse proxy, а также проверить нагрузку 20 RPS с
целевым p95 не более 500 мс.

## Баекеева Бибінұр — PostgreSQL, ER-модель и хранение данных

**Файлы:**

- `docs/er-model.md`
- `docs/postgresql-schema.md`
- `docs/security/compliance-checklist.md`

**Что рассказывает:**

Баекеева Бибінұр представляет структуру базы данных PostgreSQL 17. В ER-модель входят
таблицы:

- `users`;
- `destinations`;
- `experiences`;
- `departures`;
- `favorites`;
- `bookings`;
- `booking_status_history`.

Целостность данных обеспечивается первичными ключами, внешними ключами,
уникальными ограничениями и `CHECK`-ограничениями. База запрещает
недопустимые роли и статусы, отрицательные суммы, неправильные даты,
некорректную вместимость и повторный выезд одного тура на одну дату.

В бронировании сохраняется `experience_snapshot`. Это снимок условий тура на
момент создания заявки. Поэтому последующее редактирование каталога не меняет
уже оформленную бронь.

Рабочая база развёрнута в Docker-контейнере PostgreSQL 17. Миграции применяются
через Alembic, начальные данные загружаются через seed. Доступ к базе проходит
через API, а не напрямую из браузера.

В части хранения данных Баекеева Бибінұр объясняет, где находятся пользовательские
данные, какие роли имеют доступ к таблицам через API и почему для production
нужно дополнительно утвердить сроки хранения и резервного копирования.

## Бердебек Әмір — Trivy, Gitleaks, CI, QA и security backlog

**Файлы:**

- `docs/security/security-scan-report.md`
- `docs/security/security-backlog.md`
- `docs/qa/test-plan.md`

**Что рассказывает:**

Бердебек Әмір представляет результаты автоматического security-сканирования.

Trivy читает `backend/requirements.txt` и
`frontend/package-lock.json`, определяет версии зависимостей и сравнивает их с
базой известных CVE. Он также учитывает транзитивные npm-зависимости.

Результат Trivy:

```text
Backend: 15 уязвимостей
- 1 Critical
- 4 High
- 9 Medium
- 1 Low

Frontend: 1 High
```

Самая серьёзная находка связана с PyJWT 2.10.1:

```text
CVE-2026-102268
Critical
исправление — PyJWT 2.14.0
```

Gitleaks проверяет текущие файлы и историю Git. Он использует шаблоны,
контекст имени переменной, длину и энтропию строки. Найдено 6
секретоподобных совпадений по правилу `generic-api-key` в тестовых JWT-значениях
и старых коммитах.

Это не production-секрет из `.env`, но такие значения нельзя игнорировать:
если секрет когда-либо использовался вне тестов, его нужно немедленно заменить
и отозвать. Удаление строки из текущего файла не удаляет её из Git history.

Бердебек Әмір также представляет security backlog:

- **B-01** — добавить Trivy и Gitleaks в CI;
- **B-02** — внедрить аудит административных операций;
- **B-03** — ограничить auth/API и проверить отказоустойчивость.

В заключение он объясняет, что security scan пока не имеет статуса чистого
`PASS`, пока зависимости и секретоподобные значения не проверены и не
исправлены.
