# План реализации SaparTravel

Дата начала: 2026-10-23. Основание: `promt1.md`. Работа ведётся в существующем
репозитории; исходные миграции, учебные документы и рабочая БД сохраняются.

## Фактический аудит

- FastAPI + SQLAlchemy 2, React 19 + Router 7 + Vite 8, PostgreSQL 17 и Compose
  подтверждены исходниками. Имеются 24 направления/тура, три языка, роли,
  избранное, CRUD кабинетов, снимки брони и блокировка строки выезда.
- Нет платежей, возвратов, ограниченного резерва, участников, промокодов,
  отзывов, поддержки, уведомлений и восстановления пароля.
- Деньги каталога и бронирований — USD, выдаются как float. JSON используется
  для программы и услуг; требуется реляционное ядро и перенос данных.
- Демокаталог принадлежит заблокированной служебной учётной записи. Она
  останется заблокированной; отдельная явная команда подготовит активных
  демонстрационных поставщиков со случайными индивидуальными паролями.
- В Git до работы только неотслеживаемый пользовательский `promt1.md`.
- Исходные проверки запускаются на отдельном PostgreSQL 17, порт 55439,
  контейнер `sapartravel-implementation-test`; рабочий PostgreSQL не очищается.

3. **Бронь, платежи, возвраты — завершено.** Резерв 15 минут, транзакционные

   PostgreSQL concurrency, backend, build, браузерные пути всех ролей,
   исправления, Compose, актуальные ER/ADR/runbook и таблица проверок.

## Решения и координация

- Модульный монолит; отдельные прикладные сервисы commerce и identity/
  engagement. Дополнительные инфраструктурные сервисы не требуются.
- Согласованные цены API — строки Decimal с двумя знаками, новые сделки KZT.
- Старый подтверждённый статус не доказывает оплату. Финансовые операции
  возникают только из фактов провайдера; исторические валюты не складываются.
- Симулятор и частные демосценарии включаются настройкой; реальные карты
  не принимаются. Полный PAN/CVC не сохраняется и не попадает в диагностику.
- Независимые frontend, commerce и engagement задачи делегированы согласно
  прямому указанию `promt1.md`; общие API согласуются до интеграции.
- Проверки выполняются в отдельных базах; рабочая среда не сбрасывается.

## Продолжение по SOW/SLA/SLO/SLI — 2026-10-27

Предыдущие отметки «завершено» относятся к функциональному объёму и проверкам
23 октября. Они не подтверждают нагрузочные и эксплуатационные цели нового
[SOW](sow-sla-slo-sli.md). Рабочее дерево перед продолжением чистое.

1. **Повторная исходная проверка — выполняется.** Сборка frontend успешна;
   PostgreSQL-тесты, миграции и сквозные сценарии запускаются в отдельной среде.
2. **SLI-L — выполняется.** Совместимый маршрут `/api/v1/catalog`, безопасное
   наполнение 500 турами отдельной БД, внешний HTTP-тест 20 RPS / 10 минут
   после 2 минут прогрева. Критерий: p95 ≤ 500 мс, нет ошибок и пропусков
   запланированных запросов; сокращённый прогон не считается приёмкой.
3. **SLI-A — выполняется.** Версионированный контроль web → catalog → login →
   создание/отмена заявки, журнал UTC без секретов, месячная агрегация
   Asia/Almaty с кворумом двух из трёх точек и учётом отсутствующих минут.
   Инструмент не подменяет развёртывание трёх независимых внешних точек.
4. **SLI-D / проверка восстановления — выполняется.** Проверяемая копия с
   моментом данных, восстановление только в новую отдельную БД, сверка
   содержимого и отчёт о потере данных/времени проверки. Полный SLI-R требует
   пяти последовательных успешных минут пользовательского сценария.
5. **CI и комплект передачи — ожидается.** Подключить новые проверки,
   обновить runbook и результаты с точными ограничениями окружения.

Независимые инструменты нагрузки и доступности делегированы согласно
разделу 17 [задания](../promt1.md). Эксплуатационные секреты и рабочие данные
не используются для наполнения или очистки. Docker daemon сейчас недоступен;
для локальной верификации проверяется отдельный PostgreSQL 17 без Docker.
