## Практическая блокировка красного CI

Создан [PR #86](https://github.com/Akira-vs96/SaparTravel/pull/86) с одним
намеренно падающим тестом только во временной ветке. В
[прогоне 42172368098](https://github.com/Akira-vs96/SaparTravel/actions/runs/42172368098)
обязательная проверка backend завершилась failure. GitHub вернул
`mergeable_state=blocked`; обычная команда `gh pr merge --squash` без
`--admin` отклонена политикой ветки, код выхода 1. PR закрыт без слияния.

Одобрение независимого ревьюера также отсутствовало: опыт доказывает отказ
обычного слияния при красном CI, но не изолирует влияние единственной
проверки от требования review. Право администратора на прямой push
сохранено по прежнему требованию владельца: `enforce_admins=false`.
[Полный протокол](evidence/red-ci-proof.json) содержит исходные URL,
результаты jobs и ответ команды слияния.

## Четыре DORA-метрики

Недельное окно: 30.10.2026 06:29:57–06.11.2026 06:29:57 UTC.
Среды не смешиваются. У нового изолированного стенда всего три реальные
попытки в один день, поэтому частота за неделю не описывает устойчивый
темп команды. Для основного сайта полнота более ранней истории неизвестна.

| Метрика | Основной сайт | Изолированный стенд восстановления | Уровень относительно целей проекта |
|---|---:|---:|---|
| Успешных развёртываний / неделя | 1 | 1 | Ниже цели ≥2/неделю |
| Медиана commit→success | 0,513889 ч | 0,626944 ч | В пределах цели ≤1 ч |
| Неудачных попыток / завершённых | Неизвестно: нет полного журнала | 2/3 = 66,67% | Выше целевого предела 15% |
| Медиана восстановления | Не измерялась | 0,905487 мин | В пределах цели ≤15 мин |

Это оценка по числовым целям данного проекта. Устойчивый уровень команды
Elite/High/Medium/Low по столь короткой выборке не установлен. Контролируемые
отказы выделены в отдельную среду; они не считаются случайными сбоями
основного сайта. Используются четыре метрики из методички; актуальная
[документация DORA](https://dora.dev/guides/dora-metrics/) описывает развитие
набора показателей и необходимость сравнивать сопоставимые условия.

Частота = число success / длительность окна в неделях. Lead time — от
времени commit до подтверждённого success. CFR = число различных deployment
ID с инцидентами / число завершённых попыток. Recovery — медиана интервалов
из журнала; для чётной выборки берётся среднее двух центральных значений.
Начало отказа в этом запуске — время его регистрации GitHub после HTTP 503;
задержка регистрации не измерялась, поэтому это наблюдаемые интервалы от
записи, а не точное время начала пользовательского воздействия.

## Что требует отдельного подтверждения

Правило жизни ветки ≤3 дней записано в Wiki; согласие остальных участников
не подтверждено. Шаги 8–9 реализованы через проверенный функциональный
эквивалент: временный `GITHUB_TOKEN` с read-only разрешениями в

без хранения личного токена. Личный fine-grained PAT не создавался;
это отличие от буквального способа из методички указано в реестре.
Фактические человеко-часы команды с сентября также неизвестны.

Наличие этих файлов не заменяет независимое review или согласие команды.
