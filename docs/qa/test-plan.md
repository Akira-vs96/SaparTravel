# Тестирование SaparTravel

## Автоматические проверки

API-тесты находятся в `backend/tests/`. Зависимости: `backend/requirements-dev.txt`. Запуск из `backend/`: `pytest -q`.

Без `TEST_DATABASE_URL` используется изолированная SQLite-база. Она подходит для проверки контрактов и прав, но не доказывает корректность блокировок PostgreSQL. Интеграционный запуск получает `TEST_DATABASE_URL=postgresql+psycopg://.../sapartravel_test`; имя базы должно оканчиваться на `_test`. Тестовые таблицы пересоздаются, поэтому адрес рабочей базы использовать нельзя.

GitHub Actions запускает PostgreSQL 17, применяет и сверяет миграции, проверяет повторный seed, выполняет API-тесты. Отдельная задача устанавливает зависимости через `npm ci` и собирает React-приложение. Затем `tests/browser_smoke.py` выполняет ключевые сценарии в Chromium на запущенных API и frontend.

## Проверяемые правила

- Регистрация выдаёт роль туриста; пароль хешируется, дубли email отклоняются.
- Некорректный пароль, истёкший или поддельный JWT не открывают защищённые данные.
- Скрытые туры отсутствуют в публичной выдаче, поиск и фильтры работают совместно.
- Тексты каталога выбираются по `lang=ru|kk|en`; пагинация и сортировка стабильны.
- Избранное принадлежит конкретному пользователю; повторное сохранение не создаёт дубль.
- Сервер рассчитывает сумму по цене выбранного выезда, а не по значению клиента.
- Бронь не создаётся на прошедшую дату или сверх вместимости; два параллельных запроса на последнее место не могут оба пройти.
- Отмена освобождает места; турист не может отменить чужую или начавшуюся поездку.
- Поставщик видит и изменяет только свои туры и связанные бронирования.
- Статусы меняются по правилам; завершение до окончания поездки запрещено.
- Изменение каталога не меняет сохранённые условия брони.
- Последний администратор не может лишить систему административного доступа.

## Проверка в браузере

1. Открыть главную и каталог. Проверить поиск, страны, континенты, цену, длительность, категории, сортировку, сброс и страницы выдачи.
2. Переключить RU → KK → EN. Проверить меню, карточку тура, формы и сообщения.
3. Зарегистрироваться; обновить страницу и убедиться, что профиль доступен. Изменить имя.
4. Добавить тур в избранное, перезагрузить страницу, затем удалить его.
5. Открыть тур, выбрать выезд и число людей. Создать заявку, проверить номер, даты и стоимость в личном кабинете. Отменить заявку.
6. Войти администратором. Создать направление и тур, добавить выезд, проверить публикацию и снятие с публикации.
7. Назначить тестовому пользователю роль поставщика. Проверить его кабинет и отсутствие доступа к предложениям другого владельца.
8. Создать заявку туристом и подтвердить её поставщиком/администратором.
9. Повторить основной сценарий на ширине 390px; проверить меню, доступность кнопок, отсутствие горизонтального скролла и работу форм с клавиатуры.
10. Отключить API: интерфейс должен показать ошибку и повторную попытку, а не подменить данные демонстрационным fallback.

Для проверок используйте отдельную среду и вымышленные контакты. Бронирование не вызывает платёж, письмо или сообщение внешнему получателю.

## Приёмка и ограничения

Сборка и тесты должны завершаться успешно, основные действия в браузере — без ошибок JavaScript. Тесты не являются доказательством заявленного SLA или результатов нагрузочного тестирования. Производительность, восстановление из резервной копии и публичное HTTPS-размещение проверяются отдельно перед реальным запуском.

`tests/browser_management.py` проверяет через браузер создание направления, переводов и программы тура, расписание выездов, публикацию, редактирование и снятие с публикации. Требует `E2E_ADMIN_EMAIL/PASSWORD`, создаёт уникальные тестовые записи и оставляет проверенный тур неопубликованным. Запускается в CI после общего браузерного сценария.
