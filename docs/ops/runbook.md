# Запуск и эксплуатация SaparTravel

## Локальный запуск

```bash
python3 scripts/setup_env.py
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 api
```

Сайт доступен на http://localhost:5173. API: http://localhost:8000/docs. `/api/v1/health` проверяет соединение с PostgreSQL. API ждёт готовности БД, выполняет миграции и seed, затем запускает Uvicorn. Nginx отдаёт SPA и проксирует `/api/` к API.

`.env` содержит секреты; скрипт создаёт его с правами 0600 и никогда не перезаписывает существующий файл. Для входа администратора используются `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Не передавайте `.env` в Git и не публикуйте его в артефактах CI.

## Supabase PostgreSQL

Приложение использует Supabase как обычный PostgreSQL: браузер подключается только к API, а ключи Supabase и пароль БД не передаются frontend. Создайте `SUPABASE_DATABASE_URL` в локальном `.env` в формате `postgresql+psycopg://.../postgres?sslmode=require`. Не вставляйте секрет в исходники, команды оболочки или Git. Если пароль был опубликован, сначала смените его в Supabase и используйте только новый.

```bash
docker compose up --build -d api web
docker compose logs --tail=100 api
```

При старте API выполняет `alembic upgrade head`, создавая таблицы из миграций, затем запускает идемпотентное demo-наполнение согласно `SEED_DEMO_DATA`. При ошибке сети на прямом порту `5432` проверьте IPv6-доступность проекта; при необходимости используйте URI Supabase Session Pooler с тем же `postgresql+psycopg` драйвером и `sslmode=require`. Не запускайте backend-тесты против рабочей базы: они могут создавать и очищать таблицы. Для NFR-03 используйте отдельную тестовую БД/проект PostgreSQL.

## Проверка перед релизом

1. Прогнать API-тесты с PostgreSQL и `npm run build`.
2. На отдельной базе проверить `alembic upgrade head` и `alembic check`.
3. Проверить регистрацию, поиск, создание и отмену брони, доступ к чужим данным и кабинеты разных ролей.
4. Проверить три языка и узкий экран.
5. Сделать резервную копию рабочей базы и проверить её восстановление в отдельной среде.

## Резервное копирование

Из корня репозитория:

```bash
bash scripts/backup_db.sh
```

Архив появляется в `backups/`; эта папка исключена из Git. Для регулярных копий настройте отдельное расписание и защищённое хранилище вне сервера приложения. Сам репозиторий не включает работающий внешний мониторинг или автоматическое расписание копий.

Проверить содержимое архива:

```bash
docker compose exec -T db pg_restore --list < backups/FILE.dump
```

Восстановление проверяйте в отдельную пустую базу `sapartravel_restore`, сохраняя рабочую базу:

```bash
docker compose exec -T db createdb -U sapar sapartravel_restore
docker compose exec -T db pg_restore -U sapar -d sapartravel_restore --no-owner --no-acl < backups/FILE.dump
```

Имя `FILE.dump` замените на существующий файл. Повторное создание базы с тем же именем завершится ошибкой; существующие базы команды не удаляют.

## Обновление и откат

Перед обновлением сохраните резервную копию и версию развёрнутого кода. После обновления выполните `docker compose up --build -d` и smoke-проверки. При ошибке верните предыдущую версию приложения. Если новая миграция несовместима с прежней версией, сначала проверьте стратегию восстановления на копии базы; автоматический downgrade данных в runbook не выполняется.

`docker compose down` сохраняет volume. `docker compose down -v` удаляет хранилище и предназначен только для осознанного сброса ненужной локальной базы.

## Публичное размещение

- Используйте собственный домен и HTTPS через внешний reverse proxy.
- Задайте собственные секреты, адрес администратора и точный `CORS_ORIGINS`.
- Отключите демонстрационное наполнение для новой коммерческой базы; уже добавленные записи переменная не удаляет.
- Опубликуйте проверенные предложения и согласуйте порядок подтверждения/оплаты с поставщиками.
- Не открывайте PostgreSQL в интернет; Compose публикует его только на loopback.
- Настройте внешние проверки `/api/v1/health`, сбор логов, ротацию и алерты.
- Ограничение частоты авторизации в API хранится в памяти процесса. При нескольких репликах нужен общий лимит на шлюзе или Redis.
- JWT используется как bearer token; клиент хранит сессию в браузере. Защищайте приложение от XSS и сторонних скриптов. Выход очищает локальную сессию, но не отзывает уже выданный токен до его истечения.

## Диагностика

| Симптом | Проверка |
|---|---|
| Docker недоступен | Убедиться, что Docker Engine запущен и пользователь имеет доступ к его сокету. |
| API не запускается | Проверить обязательные `DATABASE_URL`, `JWT_SECRET`, доступ к БД и ошибки миграции в логах. |
| Ошибка подключения к БД после смены пароля | Изменение `.env` не меняет пароль внутри существующего volume; согласовать пароль PostgreSQL с конфигурацией. |
| Пустой каталог | Проверить `SEED_DEMO_DATA`, публикацию туров и активные фильтры. |
| Нет свободных дат | Добавить будущие выезды; seed не продлевает расписание автоматически. |
| 401 | Войти заново; токен ограничен по времени. |
| 403 в кабинете | Проверить текущую роль и владельца предложения. |
| 409 при бронировании | Места или состояние выезда изменились; обновить карточку. |
| 429 при входе | Дождаться окончания окна ограничения частоты запросов. |
