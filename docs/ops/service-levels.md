# Эксплуатационные проверки SOW

Техническая реализация требований [SOW/SLA/SLO/SLI](../sow-sla-slo-sli.md).
Команды выполняются из корня репозитория. `.venv/bin/python` заменяется на
интерпретатор установленного окружения. Пароли и DSN задаются в приватном
окружении, а не в аргументах команд или отчётах.

## Реализованные измерения

| Показатель | Источник / инструмент | Правило |
|---|---|---|
| SLI-A | `scripts.availability_probe`, `scripts.availability_report` | Полный пользовательский сценарий каждую минуту; кворум 2/3; весь календарный месяц Алматы |
| SLI-L | `scripts.prepare_catalog_load`, `scripts.catalog_load` | 500 туров; 20 RPS; 120 с прогрева + 600 с измерения; p95 ≤ 500 мс; ноль ошибок/потерь |
| SLI-R | `scripts.recovery_acceptance`, `scripts.recovery_report` | Реальный отказ собственного тестового API, восстановление БД, пять последовательных контрольных минут |
| SLI-D | `scripts.database_recovery`, `scripts.ops_jobs` | Проверенный согласованный snapshot, checksum и совпадение всех таблиц после restore; RPO ≤ 86400 с |
| SLI-S | `/api/v1/manage/support-metrics` | Первая содержательная реакция сотрудника, P1/P2/P3 отдельно, выборка по месяцу срока реакции |

Сохранённые фактические результаты: [отчёт](../verification-results.md) и
[JSON-доказательства](evidence/2026-10-30/). Короткий профиль не подтверждает
приёмку. Три клиента на одном компьютере не являются независимыми внешними узлами.

## Календарь и реакция поддержки

Скопируйте [пример календаря](../../config/support-calendar.example.json)
в отдельную версионированную конфигурацию. Заполните праздники и переносы
рабочих дней **по согласованному сторонами календарю**, его период действия
и ссылку на согласование. Только затем задайте `approved: true`.
В Compose задайте `SUPPORT_CALENDAR_FILE=/app/config/ИМЯ.json`: каталог `config`
передаётся API и worker только для чтения. Для локального API используйте абсолютный путь.

Окно поддержки: 09:00–18:00 Asia/Almaty, понедельник–пятница; `holidays`
исключает даты, `working_days` добавляет рабочие выходные. P1 — 15 рабочих
минут, P2 — 60, P3 — 540. При отсутствии согласованного файла работает явно
демонстрационный календарь будней; отчёт не удостоверяет договорный SLA.
Календарь и срок фиксируются в обращении; изменение файла не переписывает историю.

Сотрудник подтверждает приоритет и отправляет сообщение с принятием обращения
и следующим шагом, оставляя включённой отметку первой реакции. Backend требует
не менее 20 символов и проверяет роль/владельца. Обычное сообщение или
автоматическое письмо само по себе не фиксирует SLA-реакцию. Приоритет можно
уточнить до первой реакции; срок всегда считается от исходной регистрации,
а изменение попадает в аудит. Повторная реакция не переписывает первую.

Старые обращения не получают выдуманных сроков и реакций миграцией. Они
отмечаются как `unknown_deadlines`; отсутствие обращений — `no_data`/`null`.
Для P1 сотрудник затем обновляет статус каждые 30 рабочих минут до
восстановления, для P2 — каждый рабочий день; сообщения и смены статуса
сохраняются с автором и временем. Для P3 план решения фиксируется в переписке.

Manager/admin получает агрегат по `GET /api/v1/manage/support-metrics?month=YYYY-MM`.
Vendor видит только относящиеся к нему обращения. Журнал без текста, имён
и контактных данных: `/api/v1/manage/support-metrics/evidence?month=YYYY-MM`.
Текущий месяц помечается `finalized: false`, в него входят только уже наступившие
сроки. Для месячного отчёта сохраните завершённый агрегат как `support-YYYY-MM.json`.

## Подготовка внешних точек SLI-A

На согласованном сервере приложения, с его явно выбранным окружением:

```bash
cd backend
../.venv/bin/python -m app.monitoring \
  --deployment-id AGREED_DEPLOYMENT --origin https://AGREED_HOST \
  --directory /PRIVATE/monitoring-config \
  --points point-a point-b point-c --scope operational
```

Команда создаёт отдельные случайные доступы технических туристов и скрытый
контрольный тур. Прежние данные и секреты не перезаписываются. Технический
тур и технические аккаунты могут бронироваться только вместе. Такие брони
имеют `is_synthetic=true` и исключены из оборота, количества броней, загрузки
бизнес-выездов и CSV. Ни одной реальной оплаты контрольный сценарий не выполняет.

Опубликуйте **только** `sapartravel-monitoring.json` по
`/.well-known/sapartravel-monitoring.json` на том же origin. Для Nginx можно
смонтировать его отдельным read-only файлом в `/usr/share/nginx/html/.well-known/`.
Каждому из трёх независимых узлов передайте только его JSON-конфигурацию и
приватный `.env` (0600). Секреты не размещаются в public/frontend или JSON-журналах.
Контрольный выезд создаётся на год вперёд; его замену и конфигурацию следующего
периода согласуйте до начала нового окна измерения, не меняя прошедшие журналы.

Разовый запуск на каждом узле:

```bash
.venv/bin/python -m scripts.availability_probe \
  --config /PRIVATE/point-a.json --output /PRIVATE/point-a.jsonl
```

`SLI_EMAIL` и `SLI_PASSWORD` загружаются из приватного окружения. Для операционной
проверки нужен соответствующий safety manifest; без него probe не выполняет
вход или запись. Неверное содержимое HTTP 200, тайм-аут и пропуск — неуспех.
На внешних узлах установите `tests/requirements-browser.txt` и выполните
`python -m playwright install --with-deps chromium`: operational-проверка
`sli-a-v2` исполняет React и проверяет критические ресурсы/API. Без браузера
она завершается неуспехом, не переходя к упрощённому успешному HTML-результату.
Подготовка пустого браузера выполняется до запуска секундомера сценария,
закрытие — после; навигация и отрисовка web-шага ограничены 2 секундами.

## Расписание, резервные копии и проверки

Используйте [пример окружения](../../config/ops.env.example), сохранив заполненный
файл вне Git с правами 0600. Пробным внешним узлам не передаются DSN БД.
На backup-узле нужны клиенты PostgreSQL 17, зависимости backend и доступ
к защищённому хранилищу вне сервера приложения. `BACKUP_COPY_DIRECTORY`
должен указывать на отдельно защищённое/смонтированное хранилище; другой
локальный каталог сам по себе не означает off-site backup.

Сначала проверьте задания вручную:

```bash
.venv/bin/python -m scripts.ops_jobs probe
.venv/bin/python -m scripts.ops_jobs backup
.venv/bin/python -m scripts.ops_jobs age
.venv/bin/python -m scripts.ops_jobs restore
```

Каждое задание использует блокировку от перекрытия запусков. Копия получает
checksum, точку согласованного snapshot и fingerprint всех таблиц. Вторая
копия проверяется повторно. Restore всегда создаёт **новую** БД с суффиксом
`_test`, сверяет её содержимое и не выполняет DROP/clean рабочей базы.
Созданные учебные БД удаляются оператором отдельно после просмотра отчёта.
Возраст считается от точки данных, а не времени завершения загрузки архива.
Повреждённая последняя копия не скрывается выбором более старой.

Генерация и включение пользовательских systemd timers:

```bash
.venv/bin/python -m scripts.install_ops_timers \
  --environment-file /PRIVATE/point-a.env --enable probe
# На отдельном backup/report-узле с его собственным окружением:
.venv/bin/python -m scripts.install_ops_timers \
  --environment-file /PRIVATE/ops.env --enable backup age restore report
systemctl --user list-timers 'sapartravel-*'
systemctl --user --failed
journalctl --user -u 'sapartravel-*'
```

Probe запускается каждую минуту, backup — раз в 6 часов, контроль возраста —
ежечасно, restore — первого числа в 04:00, месячный отчёт — первого числа
в 06:00. Время запуска timer берётся из зоны узла; для отчёта границы месяца
всегда Asia/Almaty. При необходимости назначьте зону узла Asia/Almaty.
Для работы после logout/перезагрузки владелец инфраструктуры включает linger
для сервисного пользователя или устанавливает аналогичные системные units.
Сбой имеет ненулевой exit code и запись в журнале; ответственный оператор
подключает принятый в эксплуатационном контуре канал аварийного оповещения.

Без `--enable` установщик только генерирует units: это удобно для проверки и
передачи. Включение требует существующего приватного окружения. Units не
содержат пароли. Здесь не утверждается, что внешние узлы уже развёрнуты.

## Месячный отчёт и исключения

Соберите оригинальные JSONL трёх узлов в `MONTHLY_INPUT_DIRECTORY/observations/`.
Добавьте `deployment.json` по [примеру](../../config/deployment.example.json),
агрегат `support-YYYY-MM.json`, реальные JSON восстановления в `recoveries/`
и согласованный `agreement-YYYY-MM.json` по [шаблону](../../config/sla-agreement.example.json).

Шаблон соглашения намеренно не утверждён. После согласования укажите ссылку
на соглашение, контур/месяц, независимость точек и плату
`"fee": {"amount": "1000.00", "currency": "USD"}` (только если она действительно согласована).
Исключения имеют вид:

```json
{
  "start_utc": "2026-10-05T05:00:00+00:00",
  "end_utc": "2026-10-05T05:10:00+00:00",
  "reason": "Согласованная причина по договору",
  "evidence_reference": "INC-номер/журнал",
  "approval_reference": "Решение уполномоченных сторон"
}
```

Разрешены только целые минуты внутри окна. Один и тот же набор исключается
из SLA-числителя и знаменателя, SLO остаётся полным. Релизы, сбой собственного
хостинга и отсутствие мониторинга не становятся исключением автоматически.
Для операционного SLA нужны согласованное соглашение и независимые точки;
локальный acceptance-режим не получает такой статус.

```bash
.venv/bin/python -m scripts.ops_jobs report
```

Либо соберите отчёт явными файлами через `scripts.monthly_service_report --help`.
В отчёте есть покрытие и пропуски, SLO/SLA, error budget, исключения, реакции,
проверки восстановления и расчёт предложенного кредита. Пороги и лимиты
соответствуют SOW: 5/10/25%, P1 — 2% за нарушение до 10%, общий максимум 25%.
Деньги считаются Decimal. Отсутствующие наблюдения, календарь, плата или
агрегаты не подменяются успешным SLA или начислением компенсации.

## RTO и CI

В отдельном заранее созданном PostgreSQL `*_test`, указав
`RECOVERY_DATABASE_URL` в приватном окружении:

```bash
npm --prefix frontend run build
.venv/bin/python -u -m scripts.recovery_acceptance \
  --output test-results/recovery.json --probe-output test-results/recovery-probes.jsonl
```

Инструмент сам поднимает отдельные API/web процессы, подтверждает исходный
пользовательский сценарий, останавливает **свой** API, подтверждает отказ,
восстанавливает копию в новую БД и запускает API с ней. Пять наблюдений
разделены реальными минутами. `--interval 1` — только smoke, никогда приёмка.
RTO считается до первой минуты успешной серии; окончательная уверенность
возникает после пятой. Локальный результат не заменяет измерения при реальном
инциденте и трёх независимых внешних точках.

[Основной CI](../../.github/workflows/ci.yml) выполняет API, миграции, unit-инструменты
и семь браузерных сценариев. [Service level acceptance](../../.github/workflows/service-level-acceptance.yml)
проверяет полный 12-минутный профиль и реальное восстановление на PostgreSQL 17.
Удалённый запуск GitHub Actions фиксируется отдельно от локальных результатов.
