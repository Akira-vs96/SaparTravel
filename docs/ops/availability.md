# Контрольный сценарий доступности SLI-A

Основание: [SOW/SLA/SLO/SLI, раздел 5.1](../sow-sla-slo-sli.md). Реализованы [однократная проверка одной точки](../../scripts/availability_probe.py), [месячный агрегатор](../../scripts/availability_report.py) и [автоматические проверки](../../tests/test_availability.py). Нужны Python 3.12+, системная база часовых поясов и Playwright/Chromium для браузерной проверки; для жёсткого HTTP-тайм-аута нужен POSIX и запуск в главном потоке отдельного процесса.

Три независимые внешние точки, расписание и эксплуатационное хранение журналов **не развёрнуты**. Наличие инструмента и успешные unit-тесты не подтверждают доступность 99,9%. Стенд по умолчанию не опрашивается; рабочая база не изменяется. Приёмочные измерения не подтверждают SLA рабочего сервиса.

## Изоляция данных и подготовка стенда

По умолчанию probe создаёт и отменяет заявку только на отдельном приёмочном
стенде. Для эксплуатационного режима используется `app.monitoring`: скрытый
технический тур, технические аккаунты, `is_synthetic` и исключение из аналитики.
Подробности и правила safety manifest: [service-levels](service-levels.md).
Обычные аккаунты и произвольная пометка notes не заменяют эту изоляцию.

Владелец стенда до запуска:

1. Подтверждает отдельные базу, origin и секреты приёмочного контура; присваивает ему неизменный `deployment_id`.
2. Создаёт выделенного traveler через обычный интерфейс и отдельный опубликованный тестовый тур/будущий выезд через кабинет поставщика. Нужны минимум один участник и свободное место; дату выезда необходимо обновлять заранее. Скрипт не регистрирует пользователей и не создаёт туры автоматически.
3. Оставляет обычный auth rate limit включённым. Для одной проверки в минуту достаточно штатного лимита; 429 считается неуспехом. Нельзя отключать ограничение на рабочем или приёмочном стенде ради хорошей метрики.
4. Публикует на **том же origin**, что и web/API, статический `/.well-known/sapartravel-monitoring.json` со следующим точным содержимым. Файл размещается только в конфигурации приёмочного прокси, не в общем frontend-образе:

```json
{
  "scope": "acceptance-only",
  "deployment_id": "acceptance-2026-10",
  "origin": "https://acceptance.example.invalid",
  "tour_slug": "sli-acceptance-tour",
  "departure_id": "replace-with-test-departure-id",
  "isolated_database": true
}
```

Прокси должен отвечать `Content-Type: application/json` на этот путь, не перенаправлять его и проксировать `/api/v1/` в API той же приёмочной базы. При отсутствии или несовпадении manifest сценарий завершается **до передачи пароля и создания заявки**. Manifest — технический предохранитель от ошибочного origin; достоверность утверждения об отдельной базе обеспечивает владелец стенда. Это не механизм проверки удалённого подключения к БД. Публикация такого manifest на рабочем домене запрещена регламентом.

## Запуск одной точки

Создать локальную конфигурацию без секретов, например вне репозитория:

```json
{
  "point": "point-a",
  "deployment_id": "acceptance-2026-10",
  "origin": "https://acceptance.example.invalid",
  "tour_slug": "sli-acceptance-tour",
  "departure_id": "replace-with-test-departure-id",
  "browser": true
}
```

`SLI_EMAIL` и `SLI_PASSWORD` передаются процессу из защищённого хранилища окружения; не включать их в аргументы команды, Git, cron-строку, JSONL или отчёт. Не включать shell tracing. Запускать из корня репозитория:

```bash
.venv/bin/python -m scripts.availability_probe --config /secure/sli-point-a.json --output /secure/sli-point-a.jsonl
```

Коды завершения: `0` — успешный сценарий; `1` — точка неуспешна; `2` — неверная конфигурация или ошибка сохранения. Планировщик должен сохранять ненулевой код и не выполнять автоматические повторы в той же минуте. Заранее создать каталог журналов с доступом только мониторинговой учётной записи; новый файл создаётся с правами `0600`, существующие права оператор проверяет отдельно. Ротация и передача журналов сохраняют эти права.

Одно внешнее место запуска обеспечивает одну точку. Для целевой схемы нужны три заранее зарегистрированные точки на независимых хостах/сетях; три процесса на одном сервере независимость не обеспечивают. На каждой точке настроить единственный запуск каждую минуту и синхронизацию UTC-часов; внешние журналы защищать от подмены. Планировщик и независимость — отдельная эксплуатационная задача.

## Что проверяется

Версия `sli-a-v2` выполняет последовательно:

| Шаг | Ожидаемый результат |
|---|---|
| isolation | Точное соответствие приёмочного manifest настройкам точки |
| web | HTTP 200, HTML SaparTravel; при `browser: true` Chromium исполняет React и показывает каталог |
| catalog | `GET /api/v1/catalog?page_size=100`: HTTP 200 и непустой каталог корректной структуры |
| tour | Опубликованный выделенный тур с заданным будущим выездом и свободным местом |
| login | Вход технического traveler, непустой bearer token и соответствующая учётная запись |
| create | HTTP 201, `pending`, заданный выезд и один участник |
| cancel | HTTP 200, та же заявка в состоянии `cancelled` |

Каждый HTTP-запрос ограничен **2 секундами на полный ответ**, включая чтение тела; доступный остаток общего бюджета **10 секунд** может уменьшить этот лимит. Используется монотонное время; запись начала сценария содержит UTC. Редиректы запрещены, TLS проверяется штатной библиотекой, размер ответа ограничен 2 MB. HTTP 200 с неверной структурой/состоянием — неуспех. После отказа оставшиеся шаги записываются как `not_run`. Самостоятельный health endpoint не заменяет сценарий.

Версия `sli-a-v2` в operational-режиме и при `browser: true` запускает Chromium,
исполняет React, ждёт основной экран и карточку из каталога. Ошибка JavaScript
или критического ресурса/API делает web-шаг неуспешным. Для этого нужны
Playwright и Chromium из `tests/requirements-browser.txt`. Конфигурации,
создаваемые `app.monitoring`, включают браузер. Старые ручные acceptance-конфигурации
без этого флага проверяют только HTML и не подтверждают полноценную браузерную доступность.

Запуск Chromium и создание пустой страницы — подготовка измерителя до начала
сценария; закрытие браузера — после него. Эти операции не являются HTTP-запросами.
Навигация и ожидание отрисованного каталога вместе ограничены теми же 2 секундами,
а все семь шагов — 10 секундами. Ошибка подготовки браузера записывается как
неуспешная web-проверка; повторов сценария при очистке ресурсов нет.

На тайм-ауте POST сервер уже мог зафиксировать заявку. Создание не повторяется; при ошибке отмены заявка может остаться `pending` до истечения штатного резерва. Оператор проверяет такие случаи в приёмочной базе и устраняет причину; не чистит рабочую БД. Не включать очистку или повторную попытку в успешный результат первоначальной минуты.

JSONL содержит только UTC-время, идентификаторы точки/стенда/версии, scope, успех и длительность сценария и каждого шага, HTTP-код и фиксированную категорию ошибки. Тела ответов, URL, email, пароли, токены и идентификаторы заявок не сохраняются. Защита серверных журналов API на стенде настраивается отдельно.

## Месячная агрегация

Запускать после конца календарного месяца Asia/Almaty. Пример команды для **завершённого** месяца, когда уже получены реальные журналы:

```bash
.venv/bin/python -m scripts.availability_report \
  --input /secure/sli-point-a.jsonl /secure/sli-point-b.jsonl /secure/sli-point-c.jsonl \
  --month 2026-10 --points point-a point-b point-c \
  --deployment-id acceptance-2026-10 --output /secure/availability-2026-10.json
```

Использовать только реально существующие файлы. При наличии одной точки передать её файл, сохранив все три запланированных имени в `--points`: два отсутствующих источника останутся пропусками. Не создавать фиктивные точки или успешные строки. Для отсутствия всех данных допустим пустой входной файл: результат будет `status=no_data`, `availability_percent=null`, `slo_met=null`.

Правила зафиксированы в коде:

- Окно включает **все** минуты завершённого месяца; границы рассчитываются через `ZoneInfo("Asia/Almaty")`. Например, октябрь 2026: `[2026-09-30 19:00 UTC; 2026-10-31 19:00 UTC)`.
- Запись относится к минуте **начала** сценария. Для одного `deployment_id` и версии заранее нужны ровно три различных имени точки. Нельзя менять имена/версию внутри месяца ради улучшения отчёта.
- Успешны минимум две точки из трёх. Проверяются все шаги и временные лимиты, одного флага `success` недостаточно. Отсутствующая точка, неправильные шаги или длительность — неуспех. Несколько записей одной точки за минуту консервативно считаются неуспехом этой точки.
- Записи другого стенда/версии/точки, времени вне месяца и повреждённые строки явно подсчитываются как ignored; они не заполняют пропуски. Ошибки входных файлов не подменяются пустыми данными.
- Показываются покрытие, число пропущенных точек, дубликаты, успешные/неуспешные минуты, SLO 99,9% и бюджет ошибок. При полном отсутствии наблюдений процента/успешного SLO нет; все минуты остаются консервативно неуспешными.
- Незавершённый месяц отклоняется. По умолчанию считается SLO без исключений.
  Для SLA предусмотрены `--scope operational --agreement ФАЙЛ`: только
  согласованные исключения из одинаковых числителя и знаменателя, при
  подтверждённой независимости точек. Расчёт кредита выполняет
  `scripts.monthly_service_report`; инструкция — [service-levels](service-levels.md).

Собранный из одной точки месяц не может подтвердить правило 2/3. Отчёт с пропусками отражает недостаток доказательств, а не измерение реального простоя с точностью до минуты. Полный эксплуатационный SLA требует утверждённых источников, независимости точек, границ контура и процедуры исключений из [основного документа](../sow-sla-slo-sli.md).

## Проверка инструментов

```bash
.venv/bin/python -m unittest discover -s tests -p test_availability.py -v
```

Тесты проверяют тайм-аут полного чтения тела, запрет редиректа, остановку до записи без safety manifest, действительные поля API, отсутствие секретов в результате, 2/3, пропуски, дубликаты, отсутствие данных, границы Almaty, високосный месяц и запрет итогового отчёта за незавершённый месяц. HTTP transport подменён в unit-тестах; реальный внешний стенд и три точки этой командой не проверяются.
