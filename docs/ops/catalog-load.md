# Приёмочная нагрузка каталога: SLI-L

Профиль из [SOW/SLA/SLO/SLI](../sow-sla-slo-sli.md#52-sli-l-задержка-каталога): ровно 500 опубликованных туров, 20 HTTP-запросов/с, 120 секунд прогрева, затем 600 секунд измерения. Условие приёмки — p95 ≤ 500 мс, без ошибок и потерь запросов. API предоставляет один контракт по `/api/v1/catalog` и `/api/v1/experiences`; проверяется первый адрес.

## Выделенный стенд

Используйте PostgreSQL и отдельную заранее созданную БД с именем, оканчивающимся на `_test`, например `sapar_catalog_load_test`. Подготовка требует явную переменную `CATALOG_LOAD_DATABASE_URL`, отказывается работать с непустой БД, не удаляет записи и не использует рабочие `DATABASE_URL`/`.env`. Не запускайте стенд API с рабочими настройками. Пользователь тестовой БД должен иметь права на миграции и запись; создание самой БД выполняется отдельно.

Команды выполняются из корня репозитория; замените адрес и пользователя на фактический тестовый PostgreSQL. Зависимости нагрузки — из [backend/requirements-dev.txt](../../backend/requirements-dev.txt), включая `httpx`.

```bash
export CATALOG_LOAD_DATABASE_URL='postgresql+psycopg://load_user@127.0.0.1:5432/sapar_catalog_load_test'
.venv/bin/python scripts/prepare_catalog_load.py
```

Подготовка применяет полную историю Alembic и размножает существующие шаблоны каталога до 500 уникальных туров: три языка, 24 направления, категории, программа, услуги, изображения и по три будущих выезда. Учётная запись владельца неактивна. JSON-манифест сохраняется в `test-results/catalog-load-fixture.json` и содержит время, имя тестовой БД и SHA-256 содержимого fixture. Для повторной подготовки используйте новую пустую тестовую БД; скрипт не выполняет очистку.

Запустите отдельный процесс API в другом терминале. Временная рабочая директория исключает чтение рабочего `.env`; `--app-dir` указывает код приложения. Здесь приведён путь текущего репозитория; на другом стенде измените его.

```bash
export CATALOG_LOAD_DATABASE_URL='postgresql+psycopg://load_user@127.0.0.1:5432/sapar_catalog_load_test'
export DATABASE_URL="$CATALOG_LOAD_DATABASE_URL"
export JWT_SECRET="$(openssl rand -hex 32)"
export ENVIRONMENT=testing ADMIN_EMAIL= ADMIN_PASSWORD=
export SEED_DEMO_DATA=false AUTH_RATE_LIMIT=20
export PAYMENT_DEMO_ENABLED=false DEMO_MAILBOX_ENABLED=false DEMO_PRIVATE_DATA=false
cd /tmp
/home/akira/IdeaProjects/SaparTravel/.venv/bin/python -m uvicorn app.main:app \
  --app-dir /home/akira/IdeaProjects/SaparTravel/backend --host 127.0.0.1 --port 18000 --workers 1
```

Клиент обращается по TCP из отдельного процесса; время включает получение полного тела HTTP-ответа. Для измерения опубликованного стенда укажите его origin через `--base-url`; клиент может находиться на отдельной машине. Сетевой маршрут, ресурсы, число API workers, версия PostgreSQL и ревизия должны соответствовать согласованной конфигурации. Пример локального теста не устанавливает норматив для другого оборудования.

## Запуск и отчёт

Создайте `test-results/catalog-load-stand.json` с фактическими параметрами стенда, без паролей, DSN и персональных данных. Например:

```json
{
  "revision": "фактический git commit и описание незакоммиченных изменений",
  "api": {"host": "локальный Linux", "workers": 1, "cpu": "указать модель/лимит", "ram_mb": 4096},
  "database": {"version": "PostgreSQL 17", "name": "sapar_catalog_load_test", "cpu": "указать", "ram_mb": 2048},
  "client": {"host": "локальный Linux", "network": "loopback; отдельный процесс"}
}
```

```bash
.venv/bin/python scripts/catalog_load.py \
  --base-url http://127.0.0.1:18000 \
  --stand-config test-results/catalog-load-stand.json \
  --output test-results/catalog-load.json
```

До прогрева проверяются все 42 страницы: 500 различных ID и точный набор fixture slug. Отсутствующий endpoint, другой каталог или HTTP 200 с неверным содержимым проваливают запуск. Во время нагрузки циклически перебираются страницы и языки; ответ каждой попытки проверяется. Успех не зависит от ранее авторизованной сессии. Редиректы считаются ошибками, внешние HTTP-прокси из окружения отключены.

Генератор использует фиксированное расписание, которое не замедляется при медленных ответах. За прогрев запланированы 2400 запросов, за измерение — 12000. Опоздание отправки на целый интервал (50 мс) или исчерпание `--max-in-flight` помечает слот потерянным. Тайм-аут по умолчанию — 5 секунд; завершение последних запросов может увеличить общее время запуска. Ошибка прогрева тоже делает запуск неуспешным, но его задержки не входят в измеряемый p95.

JSON-отчёт содержит конфигурацию, версию клиента, UTC-границы запуска, запланированное и выполненное количество запросов, потери, дубликаты, HTTP-коды, ошибки, тайм-ауты, максимальное опоздание отправки, p95 и итог. p95 рассчитывается методом ближайшего ранга: элемент `ceil(0.95 × N)` отсортированных задержек. Ошибки учитываются независимо от p95; даже одна ошибка или потеря запрещает приёмку. Код выхода: `0` — проверки выполненного профиля прошли, `1` — не прошли, `2` — некорректные аргументы/конфигурация.

`accepted: true` возможен только при полном нормативном профиле и выполнении всех проверок. Для быстрой проверки инфраструктуры допустим короткий запуск, но он всегда имеет `acceptance_profile: false` и `accepted: false`, даже при `passed: true`:

```bash
.venv/bin/python scripts/catalog_load.py \
  --stand-config test-results/catalog-load-stand.json \
  --duration 5 --warmup 1 --output test-results/catalog-load-smoke.json
```

Сохраните манифест fixture, описание стенда и итоговый JSON рядом с результатами релиза. Прохождение unit-тестов или короткой проверки не подтверждает SLO-L. Не сохраняйте DSN с паролями в отчёте или описании стенда.

## Проверка самого инструмента

```bash
.venv/bin/python -m unittest discover -s tests -p test_catalog_load.py -v
cd backend
../.venv/bin/python -m pytest tests/test_catalog_contract.py -q
```

Unit-тесты проверяют расписание, nearest-rank p95, защиту БД, потери, насыщение клиента, HTTP-ошибки и неверное содержимое, включая дубликаты между страницами. API-тест проверяет совпадение контрактов `/catalog` и `/experiences`, включая фильтры и отказ валидации; он использует выделенную тестовую БД по правилам [conftest.py](../../backend/tests/conftest.py).
