# Выпуск, развёртывания и откат

Предлагаемое окно — вторник/среда 10:00–12:00 Asia/Almaty после подтверждения
стенда и принимающего. Это план, не обещание наличия production. Не выпускать
изменение в пик нагрузки или перед выходными. Координатор Delivery — Бердебек
Әмір по WBS. Для локального выпуска 06.11.2026 владелец среды и решения об
откате — владелец репозитория Akira-vs96; оператор — Codex по его запросу
«обнови и пересобери». Это отдельный выпуск в пятницу по запросу владельца;
обычные окна вторник/среда сохраняются. Внешний production не заявляется.
Результат и ссылка на проверку передаются владельцу в текущем чате;
отправка уведомлений другим людям отдельно не выполнялась.

## Термины DORA

Попытка развёртывания — фактическое применение конкретного commit и конфигурации
на **именованный стенд**, с записью GitHub Deployment, environment, SHA и временем.
Успешное развёртывание дополнительно требует рабочего health и основного сценария.
Частота считает успешные выпуски; знаменатель доли отказов включает все
завершённые попытки, включая failure/error. Основной и изолированный стенды
считаются раздельно.
Зелёный CI, сборка образа или push не являются развёртыванием. Lead time —
от commit до успешного стенда. Неудачное изменение — deployment с отказом smoke
или deployment, которому
в течение суток потребовался rollback/hotfix из-за вызванного им дефекта;
инцидент связывается с deployment ID. Время восстановления — от наблюдаемого
отказа до подтверждённого восстановления. Нет реестра — показатель неизвестен.

## Перед выпуском

1. Delivery подтверждает scope, дату, принимающего и канал уведомления.
2. PR связан с issue; обязательные CI проверки зелёные, есть review другого участника.
3. Снимок данных проверен восстановлением в новую БД; исходная версия и SHA сохранены.
4. Выполнить `alembic upgrade head` на восстановленной копии перед smoke новой
   версии: доступность БД сама по себе не подтверждает совместимость схемы.
   Проверить health **и каталог**. Сверить миграции на пустой БД и копии;
   совместимость отката описать отдельно.
5. Значения окружения проверены без печати секретов. Секреты переданы отдельно.
6. Указать среду, SHA, оператора и начать GitHub Deployment только при реальном применении.
7. По [runbook](runbook.md) применить версию и миграции, проверить health,
   основной сценарий, роли и отсутствие новых ошибок JS.
8. Только после smoke отметить deployment success; при ошибке — failure
   и запись инцидента. Сохранить фактические времена, без восстановления по памяти.

## Откат

1. **Для локального выпуска решение единолично принимает Akira-vs96**;
   оператор начинает откат по его решению. Для внешней среды сначала назначается
   дежурный владелец. Основание — потеря основного сценария, данных или
   разграничения доступа; начало — в пределах **5 минут** обнаружения.
2. Зафиксировать время, deployment ID, симптом и остановить дальнейший rollout.
3. Вернуть предыдущий совместимый образ/SHA по runbook. Не выполнять
   автоматический downgrade несовместимых миграций.
4. При повреждении данных восстановить проверенную копию в **новую** БД,
   сверить содержимое и переключить приложение согласованным действием.
5. Подтвердить восстановление пользовательским сценарием; для SLI-R —
   пять реальных успешных минут. Записать RTO/RPO и последствия.
6. Сообщить результат согласованным каналом, связать исправление с инцидентом.

## Улучшения процесса

| Изменение | Проверяемое ожидаемое улучшение | Пересчёт |
|---|---|---|
| Проверка миграций на восстановленной копии, затем health, каталог и точный SHA перед отметкой success | Устранить повтор обнаруженного отказа схемы; CFR следующих ≥10 обычных попыток ≤15%, recovery ≤5 минут | 20.11.2026 |
| Автоматический выпуск проверенного CI commit через Render Free, с GitHub Deployment и smoke | ≥5 полезных успешных выпусков в неделю; медиана commit→стенд ≤15 минут; запись 100% принятых hook попыток | 20.11.2026 |

Это цели следующего цикла, а не замена измеренных результатов. Публичный
учебный стенд выпускается после готового изменения и успешного CI, без ожидания
еженедельного ручного окна. Окна выше относятся к ручным локальным выпускам.
Для публичной среды используется отдельная история `public-demo` по
[инструкции бесплатной публикации](free-hosting.md). Пока аккаунты не подключены
и smoke не выполнен, внешний сайт и результаты его развёртывания не заявляются.

Отдельный отрицательный браузерный сценарий проверяет HTTP 200 с null/HTML
в каждом PR; оба ответа должны дать восстанавливаемую ошибку без JS-падения.

## Измеренные исправления и capacity

06.11.2026 на изолированном стенде зарегистрированы две неудачные попытки
и одно восстановление. От первой зарегистрированной ошибки до рабочего
каталога прошло **103,329235 с = 0,028702565 часа**. Это время простоя стенда,
не трудозатраты. Последняя автоматическая команда исправления и проверки
заняла **3,345980 с = 0,000929439 часа**; промежуточные действия не были
непрерывно хронометрированы. Два связанных отказа не удваивают эту команду.

Личные часы участников с сентября и общая фактическая capacity не измерены.
На следующий цикл предлагается **20% capacity** на надёжность: при плане
40 человеко-часов это 8 часов. Это плановый пример, а не выполненная работа.
С 06.11 вести начало/конец работы, исполнителя и deployment ID отдельно от
времени простоя; 20.11 пересчитать фактическую долю и скорректировать резерв.
