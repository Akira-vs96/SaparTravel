# SaparTravel

SaparTravel — учебное веб-приложение для поиска и бронирования туров. Турист выбирает маршрут и дату выезда, отправляет заявку и отслеживает её статус. Поставщик управляет своими турами и заявками, администратор — каталогом, направлениями и ролями пользователей.

Интерфейс и демонстрационный каталог доступны на **русском, казахском и английском** языках. Начальное наполнение содержит **24 направления и 24 тура**.

**Статус:** реализован учебный MVP. Каталог, цены и расписание демонстрационные. Онлайн-оплата, реальные туристические API и отправка email/SMS не подключены. Валюта туров и бронирований — **USD**; финансовая модель проекта в материалах ЛЗ 8 ведётся отдельно, в **KZT**.

## Возможности и роли

| Роль | Возможности |
|---|---|
| Гость | Просмотр направлений и опубликованных туров, поиск, фильтры, сортировка, пагинация, программа тура и будущие выезды |
| Турист — `traveler` | Регистрация и вход, изменение имени в профиле, избранное, создание и просмотр своих бронирований, самостоятельная отмена до начала тура |
| Поставщик — `vendor` | Создание и редактирование своих туров на трёх языках, публикация и снятие с публикации, добавление выездов, обработка заявок по своим турам |
| Администратор — `admin` | Управление всеми турами и заявками, создание и редактирование направлений, назначение ролей пользователям |

Каталог фильтруется по направлению, континенту, категории, цене и максимальной длительности. Доступны сортировки по рекомендациям, цене и рейтингу. Карточка тура содержит программу по дням, включённые и исключённые услуги, стоимость выездов и остаток мест.

Новый пользователь получает роль `traveler`. Чтобы назначить поставщика, войдите администратором, откройте `/manage`, выберите пользователей и измените роль нужного аккаунта на `vendor`. Поставщик увидит кабинет после обновления страницы. API проверяет роль и владельца ресурса при каждом защищённом запросе; понижение роли последнего активного администратора запрещено.

Основные страницы: `/` — главная, `/explore` — каталог, `/trips/:slug` — тур, `/register` и `/login` — авторизация, `/account` — профиль, `/favorites` — избранное, `/bookings` — заявки, `/manage` — управление, `/about` и `/privacy` — информация о сервисе.

## Стек и архитектура

| Слой | Технологии |
|---|---|
| Интерфейс | React 19, React Router 7, Vite 8, Lucide React, CSS |
| API | Python 3.12, FastAPI, Pydantic Settings, Uvicorn |
| Хранение данных | PostgreSQL 17, SQLAlchemy 2, psycopg 3, Alembic |
| Авторизация | JWT HS256, PyJWT, хеширование паролей Argon2 через pwdlib |
| Запуск | Docker Compose v2, Nginx для SPA и проксирования API |
| Проверки | pytest, HTTPX, Playwright / Chromium, GitHub Actions |

```text
Браузер → Nginx (Docker) / Vite (разработка) → FastAPI /api/v1 → PostgreSQL
```

Frontend обращается к API на том же origin через `/api/v1`. Строка подключения к БД и серверные секреты остаются на backend. Авторизация реализована в приложении; Supabase Auth не используется. При необходимости API может работать с PostgreSQL в Supabase через обычную строку подключения.

Точные версии зависимостей закреплены в [backend/requirements.txt](backend/requirements.txt), [frontend/package.json](frontend/package.json) и [frontend/package-lock.json](frontend/package-lock.json). Архитектурное решение описано в [ADR-002](docs/adr/ADR-002.md).

## Быстрый запуск через Docker

Требуются **Docker Engine с работающей службой**, **Docker Compose v2** и **Python 3** для генерации конфигурации. Все команды ниже выполняются из корня репозитория, если не указано другое.

```bash
python3 scripts/setup_env.py
docker compose up --build -d
docker compose ps
```

`setup_env.py` создаёт `.env` с уникальными паролями и JWT-секретом, устанавливает права `0600` и сохраняет существующий файл без изменений. Для своего адреса администратора при первом запуске:

```bash
python3 scripts/setup_env.py --admin-email your@email.com
```

Адреса при стандартных значениях портов:

| Компонент | Адрес |
|---|---|
| Сайт | http://localhost:5173 |
| Swagger UI | http://localhost:8000/docs |
| OpenAPI JSON | http://localhost:8000/openapi.json |
| Проверка API и БД | http://localhost:8000/api/v1/health |
| PostgreSQL с хоста | `127.0.0.1:5432`, база `sapartravel`, пользователь `sapar` |

Порты задаются в `.env` через `WEB_PORT`, `API_PORT` и `DB_PORT`. Если `5432` занят, установите `DB_PORT=55432`. Для локального API также измените порт в `DATABASE_URL` на `55432`. Внутри Compose соединение с локальной БД всегда идёт на `db:5432`.

При запуске контейнер API последовательно выполняет миграции, начальное наполнение и запускает Uvicorn. Frontend запускается после успешной проверки здоровья API.

```bash
curl http://localhost:8000/api/v1/health
```

Ожидаемый ответ при доступной БД:

```json
{"status":"ok","service":"sapartravel-api","database":"ok"}
```

Для входа администратором используйте `ADMIN_EMAIL` и `ADMIN_PASSWORD` из локального `.env`. По умолчанию email — `admin@example.com`, пароль генерируется случайно. Общедоступного пароля администратора нет. `.env` исключён из Git.

## Локальная разработка

Для запуска приложений на хосте нужны **Python 3.12+**, **Node.js 22.12+ с npm** и **PostgreSQL 17**. Базу можно оставить в Docker:

```bash
python3 scripts/setup_env.py
docker compose up -d db
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
npm --prefix frontend ci
```

Запуск backend из корня проекта в Bash:

```bash
(
  set -a
  source .env
  set +a
  cd backend
  ../.venv/bin/alembic upgrade head
  ../.venv/bin/python -m app.seed
  ../.venv/bin/uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
)
```

В отдельном терминале из корня проекта:

```bash
npm --prefix frontend run dev
```

В режиме разработки Vite проксирует `/api` на `http://127.0.0.1:8000`. Если backend запущен на другом порту, измените `server.proxy` в [frontend/vite.config.js](frontend/vite.config.js). `API_PORT` и `WEB_PORT` настраивают публикацию портов Compose, а не команды Uvicorn и Vite на хосте.

Для собственного PostgreSQL задайте `DATABASE_URL` в корневом `.env`. При раздельном размещении frontend и API передайте полный адрес API с префиксом `/api/v1` через `VITE_API_URL` при сборке и настройте `CORS_ORIGINS` на сервере. Compose передаёт `VITE_API_URL` из корневого `.env`; локальный Vite нужно настраивать через окружение процесса или файл окружения в `frontend/`.

## Переменные окружения

Пример конфигурации — [.env.example](.env.example), генератор — [scripts/setup_env.py](scripts/setup_env.py). Пустые поля секретов в примере нужно заполнить перед запуском; генератор делает это автоматически.

| Переменная | Назначение и значение по умолчанию |
|---|---|
| `POSTGRES_PASSWORD` | Пароль PostgreSQL в Compose; генератор создаёт случайное значение |
| `DATABASE_URL` | Подключение API на хосте: `postgresql+psycopg://…`; генератор указывает `localhost:5432/sapartravel` |
| `SUPABASE_DATABASE_URL` | Необязательная внешняя PostgreSQL-база для API в Compose; при наличии заменяет подключение к `db` |
| `JWT_SECRET` | Обязательный случайный секрет: минимум 32 символа; генератор создаёт 96 шестнадцатеричных символов |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | Пара для первоначального создания администратора; генератор задаёт email и случайный пароль |
| `SEED_DEMO_DATA` | Загрузка демонстрационного каталога; в сгенерированном `.env` и Compose — `true`, в настройках API без переменной — `false` |
| `ENVIRONMENT` | Окружение API; по умолчанию `development`, для тестов — `testing` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Срок действия JWT; по умолчанию `120`, допустимо от `5` до `10080` минут |
| `CORS_ORIGINS` | Разрешённые источники через запятую; генератор и Compose разрешают `http://localhost:5173` и `http://127.0.0.1:5173` |
| `DB_PORT` / `API_PORT` / `WEB_PORT` | Порты Compose на хосте; по умолчанию `5432` / `8000` / `5173` |
| `VITE_API_URL` | Публичный адрес API, встраиваемый в frontend при сборке; по умолчанию `/api/v1` |
| `TEST_DATABASE_URL` | Отдельная база для backend-тестов; без неё используется временная SQLite-база |
| `AUTH_RATE_LIMIT` | Лимит запросов регистрации и входа на адрес клиента в минуту; по умолчанию `20`, отключение значением `0` разрешено только в тестах |
| `LOG_LEVEL` | Уровень логирования API; по умолчанию `INFO` |

`AUTH_RATE_LIMIT` и `LOG_LEVEL` читаются настройками API, но текущий Compose не передаёт их из корневого `.env`: для изменения в контейнере добавьте их в `services.api.environment`.

`ADMIN_EMAIL` и `ADMIN_PASSWORD` должны быть заданы вместе либо оба отсутствовать. Минимальная длина пароля администратора — 10 символов. Повторный seed не меняет пароль существующего администратора; изменение `.env` само по себе не сбрасывает учётные данные в БД.

В Compose `DATABASE_URL` формируется из параметров контейнерной БД либо `SUPABASE_DATABASE_URL`. Корневая переменная `DATABASE_URL` предназначена для запуска API на хосте. Подключение внешнего PostgreSQL описано в [runbook](docs/ops/runbook.md#supabase-postgresql); Supabase Auth для этого не требуется.

## Данные и правила бронирования

Основные таблицы: `users`, `destinations`, `experiences`, `departures`, `favorites`, `bookings`, `booking_status_history`. Схема, связи, индексы и ограничения описаны в [ER-модели](docs/er-model.md) и [PostgreSQL-схеме](docs/postgresql-schema.md).

Стоимость заявки рассчитывает сервер: **цена выбранного выезда × количество путешественников**. Цена «от» в каталоге служит ориентиром. При создании бронирования сохраняются сумма, валюта, даты и снимок основных сведений о туре на трёх языках.

Жизненный цикл заявки:

```text
pending → confirmed → completed
   ↓          ↓
cancelled  cancelled
```

- Все заявки со статусом, отличным от `cancelled`, учитываются при расчёте занятых мест.
- Создание и изменение брони используют транзакции и блокировку строки выезда через `SELECT … FOR UPDATE`; конкурентные запросы повторно проверяют доступные места.
- Турист может отменить свою незавершённую заявку до даты начала тура. Повторная отмена возвращает текущее состояние.
- Подтверждать уже начавшийся выезд нельзя; статус `completed` доступен только после даты окончания.
- Изменения статуса записываются в `booking_status_history`. Поставщик обрабатывает только заявки по собственным турам.

Начальное наполнение берётся из [backend/app/seed_data.json](backend/app/seed_data.json). Повторный seed сохраняет существующие записи и изменения каталога, не продлевает расписание уже созданных туров и не обновляет их цены. Демонстрационные туры принадлежат служебному неактивному поставщику; управлять ими может администратор. Для проверки кабинета поставщика создайте отдельный аккаунт с ролью `vendor` и собственный тур.

`SEED_DEMO_DATA=false` отключает добавление демоданных, но не удаляет уже загруженные записи. Создание администратора от этой переменной не зависит.

## API

Базовый префикс — `/api/v1`. Полные схемы запросов и ответов доступны в Swagger UI работающего API. Каталог и другие локализуемые ответы принимают `lang=ru`, `lang=kk` или `lang=en`; при отсутствии перевода используется русское значение.

| Методы и путь относительно `/api/v1` | Назначение | Доступ |
|---|---|---|
| `GET /health` | Проверка API и соединения с БД | Публичный |
| `POST /auth/register`, `POST /auth/login` | Регистрация и выдача JWT | Публичный, с ограничением частоты |
| `GET /auth/me`, `PATCH /auth/me` | Текущий пользователь, изменение имени | Авторизованный пользователь |
| `GET /destinations` | Направления и количество опубликованных туров | Публичный |
| `GET /experiences`, `GET /experiences/{slug}` | Поиск и карточка опубликованного тура | Публичный |
| `GET /favorites`, `PUT /favorites/{experience_id}`, `DELETE /favorites/{experience_id}` | Избранное текущего пользователя | Авторизованный пользователь |
| `GET /bookings`, `POST /bookings` | Свои заявки и создание бронирования | Авторизованный пользователь |
| `POST /bookings/{booking_id}/cancel` | Отмена собственной заявки | Владелец заявки |
| `GET /manage/experiences`, `POST /manage/experiences`, `PATCH /manage/experiences/{experience_id}` | Управление турами | Поставщик своих туров, администратор |
| `POST /manage/experiences/{experience_id}/departures` | Добавление выезда | Поставщик своего тура, администратор |
| `GET /manage/bookings`, `PATCH /manage/bookings/{booking_id}` | Обработка заявок | Поставщик своих туров, администратор |
| `GET /manage/destinations`, `POST /manage/destinations`, `PATCH /manage/destinations/{destination_id}` | Управление направлениями | Администратор |
| `GET /admin/users`, `PATCH /admin/users/{user_id}` | Пользователи и назначение ролей | Администратор |

Защищённые запросы используют заголовок `Authorization: Bearer <access_token>`. Токен возвращается при регистрации и входе.

Пример запроса каталога:

```bash
curl 'http://localhost:8000/api/v1/experiences?lang=ru&continent=Asia&sort=price_asc&page=1&page_size=12'
```

Основные параметры поиска: `q`, `destination`, `continent`, `category`, `min_price`, `max_price`, `duration_max`, `sort`, `page`, `page_size`, `lang`. Сортировки: `recommended`, `price_asc`, `price_desc`, `rating`.

## Проверки и CI

### Backend

После установки `backend/requirements-dev.txt` запустите из корня:

```bash
(cd backend && ../.venv/bin/python -m pytest -q)
```

Без `TEST_DATABASE_URL` тесты используют временную SQLite-базу. Проверка конкурентного бронирования помечена `postgres` и пропускается без PostgreSQL. SQLite разрешена настройками приложения только в окружении `testing`.

Для проверки на PostgreSQL создайте отдельную тестовую базу в локальном контейнере и передайте её URL:

```bash
docker compose exec db createdb -U sapar sapartravel_test
(
  set -a
  source .env
  set +a
  export TEST_DATABASE_URL="postgresql+psycopg://sapar:${POSTGRES_PASSWORD}@127.0.0.1:${DB_PORT:-5432}/sapartravel_test"
  cd backend
  ../.venv/bin/python -m pytest -q
)
```

Команда `createdb` нужна один раз. Имя PostgreSQL-базы для этих тестов должно оканчиваться на `_test`. **Тесты удаляют и пересоздают таблицы: используйте только отдельную тестовую базу.** Рабочий `DATABASE_URL` автоматически не используется вместо `TEST_DATABASE_URL`.

### Frontend

```bash
npm --prefix frontend ci
npm --prefix frontend run build
```

### Браузерные сценарии

Проверки требуют работающего приложения с демонстрационным каталогом и будущими выездами. Используйте отдельную демонстрационную среду: сценарии создают пользователей, заявки и записи каталога.

```bash
.venv/bin/python -m pip install -r tests/requirements-browser.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python tests/browser_smoke.py --base-url http://127.0.0.1:5173
```

`browser_smoke.py` проверяет регистрацию, сессию после перезагрузки, профиль, избранное, бронирование и отмену, языки, фильтры, мобильное меню и ошибки API. Переменные `E2E_ADMIN_EMAIL` и `E2E_ADMIN_PASSWORD` включают административные сценарии.

Для полной проверки управления задайте эти переменные в окружении тестового процесса и выполните:

```bash
.venv/bin/python tests/browser_management.py --base-url http://127.0.0.1:5173
```

`browser_management.py` требует учётные данные администратора. Он проверяет направления, переводы, программу тура, выезды, публикацию, редактирование и назначение поставщика; созданные проверочные туры остаются неопубликованными. Скриншоты и другие результаты браузерных проверок сохраняются в `test-results/`.

### GitHub Actions

Workflow [ci.yml](.github/workflows/ci.yml) запускается при push в `main`/`master` и в pull request. Он проверяет миграции PostgreSQL и `alembic check`, повторный seed, backend-тесты с PostgreSQL, сборку frontend и оба браузерных сценария в Chromium. Артефакты браузерных проверок загружаются в Actions.

Сценарии и критерии приёмки: [план тестирования](docs/qa/test-plan.md).

## Эксплуатация и диагностика

```bash
docker compose ps
docker compose logs --tail=100 api
docker compose logs --tail=100 web
docker compose exec db psql -U sapar -d sapartravel
```

Остановка с сохранением данных:

```bash
docker compose down
```

Локальная БД хранится в volume `postgres_data`. **`docker compose down -v` удаляет volume вместе с данными.** После изменения исходников пересоберите контейнеры через `docker compose up --build -d`.

Резервная копия локальной БД Compose:

```bash
bash scripts/backup_db.sh
```

Скрипт создаёт архив `backups/*.dump`; каталог исключён из Git. При использовании внешней БД скрипт продолжает копировать контейнер `db`, поэтому резервное копирование внешней базы настраивается отдельно. Восстановление в отдельную базу и порядок обновления описаны в [runbook](docs/ops/runbook.md).

| Симптом | Что проверить |
|---|---|
| Порт `5432` занят | Изменить `DB_PORT` в `.env`; для API на хосте согласовать порт в `DATABASE_URL` |
| API не запускается | Логи `api`, готовность БД, строку подключения и обязательные секреты |
| Ошибка БД после изменения пароля | Пароль в существующем volume не меняется вместе с `.env`; согласовать пароль БД и конфигурацию |
| Пустой каталог | `SEED_DEMO_DATA`, публикацию туров и фильтры; при ручном запуске выполнить seed после миграций |
| У тура нет доступных дат | Добавить будущие выезды: повторный seed не обновляет расписание существующего тура |
| Не работает новый пароль администратора | Seed сохраняет существующий пароль; изменение `.env` не обновляет аккаунт |
| `401` / `403` | Для `401` войти заново; для `403` проверить роль и владельца ресурса |
| `409` при заявке | Обновить карточку: места, даты или статус могли измениться |
| `429` при входе | Дождаться окончания минутного окна ограничения запросов |

API пишет структурированные логи и добавляет `X-Request-ID` в ответы. Ограничение частоты авторизации хранится в памяти процесса. Выход очищает сессию в браузере; уже выданный JWT действует до истечения срока.

Для публичного размещения потребуются HTTPS, собственные секреты и CORS, внешние резервные копии, мониторинг и проверка нагрузки. При нескольких процессах API нужен общий механизм ограничения частоты запросов. Подробности — в [операционном runbook](docs/ops/runbook.md#публичное-размещение).

## Ограничения текущей версии

В MVP отсутствуют онлайн-оплата и эквайринг, реальные интеграции с отелями и туроператорами, email/SMS-уведомления, восстановление пароля по почте, мобильное приложение, пользовательские отзывы, возвраты и полноценная продуктовая аналитика. Рейтинги и счётчики отзывов в начальном каталоге — демонстрационные данные. Изображения загружаются с внешнего сервиса Unsplash.

Локальный запуск через Compose предназначен для разработки и демонстрации. Учебные прогнозы, отчёты и проверки не заменяют проверку готовности публичного сервиса к эксплуатации.
